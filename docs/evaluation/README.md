# Evidence archival sequence

This directory's contents are generated by `regenerate.sh` and are not meaningful as evidence
until they were produced from a clean checkout of a reviewed commit. That requires two separate
commits, not one, because a generated file cannot contain the hash of the commit that contains
that same generated file without creating a self-reference.

## Commit A — the reviewed implementation

Commit A contains the reviewed source: code fixes, regression tests, measurement programs
(`crates/*/examples/*.rs` used by the protocol), and the protocol scripts themselves
(`regenerate.sh`, `summarize.py`). It does **not** need to contain this directory's generated
`.txt` output files — those are reproducible from A, not part of A's own content.

## Run the protocol from a clean checkout of A

```
git checkout <commit-A-hash>
git status --porcelain   # must be empty
bash docs/evaluation/regenerate.sh
```

`PROVENANCE.txt` will record commit A as the source revision evaluated, with `working_tree:
clean`. This is the only condition under which the files in this directory should be committed
as evidence — a dirty-tree run (the normal state while a diff is still under review) produces
files that describe that dirty state honestly, but must not be treated as final.

## Commit B — the evidence artifact

Commit the regenerated files (this directory's `.txt` outputs, including `PROVENANCE.txt`
citing A) as a separate commit, B. B's own hash is never written into any file B contains —
nothing inside B needs to know B's own identity, and trying to make it self-describe that way is
the self-reference this sequence exists to avoid.

## Where B's hash actually gets recorded

Not inside B. Record it in whichever of these fits the project's release process:

- a git tag applied to B after it exists (e.g. `git tag evidence-v1 <commit-B-hash>`), or
- the paper's release / Zenodo deposit metadata (a DOI record can point at a specific commit or
  tag), or
- a later commit C -- the paper's own text, finalized after both A and B exist -- citing both
  hashes directly. This is safe specifically because C is written after A and B already exist;
  A and B citing themselves is what is unsafe.

## Citing this work

Cite **A** as "the implementation this evidence was generated from" and **B** as "the commit
containing the evidence itself." They are different claims about different commits, and neither
should be presented as if it were the other.
